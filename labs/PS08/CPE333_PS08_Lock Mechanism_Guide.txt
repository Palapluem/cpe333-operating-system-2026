1. จุดเริ่มต้นของ Lecture: Multiple Threads และ Shared Data
======================================================================

เวลาโปรแกรมมีหลาย Thread ทำงานพร้อมกัน แต่ละ Thread สามารถทำงานสลับกันได้
และถ้าหลาย Thread ต้องใช้ตัวแปรหรือข้อมูลร่วมกัน เช่น counter, balance, stock
ลำดับการทำงานที่เกิดขึ้นจริงอาจไม่เป็นแบบที่เราคาดไว้

ตัวอย่างเชิงแนวคิด:

Thread A ต้องการเพิ่ม counter
Thread B ก็ต้องการเพิ่ม counter

การเพิ่มค่า 1 ครั้งไม่ได้หมายความว่า CPU ทำทุกอย่างในคำสั่งเดียวเสมอไป
โดยแนวคิดสามารถมองเป็น:

1. Load ค่า counter
2. Add 1
3. Store ค่าใหม่กลับไป

ถ้า Thread A และ Thread B ทำขั้นตอนเหล่านี้สลับกันในจังหวะที่ไม่เหมาะสม
ค่าที่ได้สุดท้ายอาจผิด

สิ่งนี้เรียกว่า:

    Race Condition

ความหมายแบบง่าย:
ผลลัพธ์ของโปรแกรมขึ้นอยู่กับ "ใครทำก่อน ใครแทรกเมื่อไร"
ทั้งที่เราต้องการให้ผลลัพธ์ถูกต้องเสมอ

[อ้างอิง: Lecture8_LocksMechanism.pdf หน้า 2 และ 6]

2. Critical Section คืออะไร
======================================================================

Critical Section คือส่วนของโปรแกรมที่เข้าไปอ่าน/แก้ไข Shared Data
ซึ่งถ้ามีหลาย Thread เข้าไปพร้อมกันอาจทำให้ข้อมูลผิด

ตัวอย่าง:

    counter = counter + 1;

ถ้า counter เป็น Shared Variable
ส่วนนี้อาจถือเป็น Critical Section

เป้าหมายสำคัญคือ:

    ห้ามหลาย Thread เข้า Critical Section เดียวกันพร้อมกัน
    ในกรณีที่การทำพร้อมกันทำให้ข้อมูลผิด

แนวคิดนี้เรียกว่า:

    Mutual Exclusion

จำเป็นต้องเข้าใจคำ 4 คำนี้ก่อนทำ PS08:

- Shared Data
- Race Condition
- Critical Section
- Mutual Exclusion

[อ้างอิง: Lecture8_LocksMechanism.pdf หน้า 2, 5, 6]

3. Lock / Unlock และ Mutex
======================================================================

อาจารย์ใช้แนวคิด Lock เพื่อควบคุมการเข้า Critical Section

ภาพง่าย ๆ:

    Thread
      |
      v
    lock()
      |
      v
    Critical Section
      |
      v
    unlock()

ความหมาย:

- lock()
  Thread พยายามขอสิทธิ์เข้า Critical Section

- unlock()
  Thread ที่ทำงานเสร็จคืนสิทธิ์ให้ Thread อื่น

สถานะหลักของ Lock:

1. Available / Free
   = ยังไม่มี Thread ถือ Lock

2. Acquired / Held
   = มี Thread หนึ่งถือ Lock อยู่

ใน POSIX จะใช้คำว่า:

    Mutex

มาจากแนวคิด Mutual Exclusion

[อ้างอิง: Lecture8_LocksMechanism.pdf หน้า 3]

4. เกณฑ์สำคัญที่อาจารย์ใช้ประเมิน Lock
======================================================================

ส่วนนี้สำคัญมาก เพราะ PS08 ระบุว่าให้วิเคราะห์ Correctness และ Performance
"using metrics discussed in class"

จาก Lecture 8 อาจารย์ให้เกณฑ์หลักไว้ดังนี้

----------------------------------------------------------------------
4.1 Mutual Exclusion
----------------------------------------------------------------------

คำถาม:

    Lock ป้องกันไม่ให้หลาย Thread เข้า Critical Section พร้อมกันได้หรือไม่?

ถ้าสอง Thread เข้า Critical Section พร้อมกันได้
แปลว่า Lock นั้นมีปัญหาด้าน Correctness

----------------------------------------------------------------------
4.2 Absence of Deadlock
----------------------------------------------------------------------

คำถาม:

    ถ้ามีหลาย Thread ต้องการเข้า Critical Section
    ระบบยังมี Thread อย่างน้อยหนึ่งตัวที่สามารถเดินหน้าต่อได้หรือไม่?

ถ้าทุก Thread รอกันหมดและไม่มีใครไปต่อได้
เรียกว่าเกิด Deadlock

----------------------------------------------------------------------
4.3 Fairness
----------------------------------------------------------------------

คำถาม:

    Thread ที่กำลังรอมีโอกาสได้ Lock อย่างเหมาะสมหรือไม่?

ถ้ามี Thread หนึ่งรอนานมากหรือไม่ได้เข้า Critical Section เลย
ในขณะที่ Thread อื่นได้ Lock ซ้ำ ๆ
เกี่ยวข้องกับปัญหา:

    Starvation

----------------------------------------------------------------------
4.4 Performance
----------------------------------------------------------------------

ดู Overhead ของ Lock เช่น:

- ตอนที่ไม่มีใครแย่ง Lock
- ตอนที่มีหลาย Thread แย่ง Lock
- ใช้ CPU วนรอหรือไม่
- มี Context Switch / Scheduling overhead หรือไม่
- มี Retry มากหรือไม่
- เมื่อ Contention สูงแล้วทำงานแย่ลงแค่ไหน

คำว่า:

    Contention

หมายถึงหลาย Thread กำลังแข่งขันกันเพื่อ Resource/Lock เดียวกัน

[อ้างอิง: Lecture8_LocksMechanism.pdf หน้า 4]


======================================================================
5. Software Lock แบบง่าย ๆ ทำไมถึงผิด
======================================================================

Lecture ยกตัวอย่าง Lock แบบ Software ง่าย ๆ:

    flag = 0  -> Lock ว่าง
    flag = 1  -> Lock ถูกถืออยู่

แนวคิด:

    while (flag == 1);
    flag = 1;

ปัญหาคือ:

    "ตรวจค่า" และ "เปลี่ยนค่า" ไม่ได้เกิดพร้อมกันแบบ Atomic

ตัวอย่าง Interleaving:

1. Thread 0 ตรวจ flag
   พบว่า flag = 0

2. ก่อน Thread 0 จะตั้ง flag = 1
   เกิด Context Switch

3. Thread 1 เข้ามา
   ตรวจ flag และยังพบว่า flag = 0

4. Thread 1 ตั้ง flag = 1
   และเข้า Critical Section

5. กลับไป Thread 0

6. Thread 0 ตั้ง flag = 1
   แล้วเข้า Critical Section เช่นกัน

ผล:

    Thread 0 และ Thread 1 สามารถอยู่ใน Critical Section พร้อมกัน

ดังนั้น:

    Mutual Exclusion ไม่ได้ถูก Guarantee

นี่เป็นเหตุผลว่าทำไมการสร้าง Lock ต้องการ Operation ที่เป็น Atomic

[อ้างอิง: Lecture8_LocksMechanism.pdf หน้า 8-11]

6. Atomic Operation คืออะไร
======================================================================

Atomic Operation คือ Operation ที่ระบบรับประกันว่า
มองได้เหมือนเป็นการทำงาน "หนึ่งก้อนที่แบ่งแทรกไม่ได้"

    Check
    แล้วค่อย
    Set

แยกจากกัน

    Check + Set แบบ Atomic

Hardware จึงมี Primitive / Instruction สำหรับช่วยสร้าง Lock

======================================================================
7. Test-and-Set
======================================================================

Test-and-Set เป็น Hardware Instruction ที่ทำแนวคิดประมาณว่า:

1. อ่านค่าเก่าที่ Memory
2. เขียนค่าใหม่
3. ทำทั้งหมดแบบ Atomic

จึงนำมาสร้าง Lock ได้

ตัวอย่างแนวคิด:

    while (TestAndSet(lock) == 1) {
        // wait
    }

ถ้า Lock ถูกถืออยู่ TestAndSet จะทำให้ Thread รอต่อ

เมื่อใช้การวนรอแบบนี้เรียกว่า:

    Spin Lock

ข้อดี:

- ทำ Mutual Exclusion ได้
- Implementation ค่อนข้างตรงไปตรงมา

ข้อเสีย:

- Thread ที่กำลังรอใช้ CPU cycle
- บน Single Processor อาจเสียประสิทธิภาพมาก
- Fairness ไม่ถูก Guarantee
- Waiting Thread บางตัวอาจเกิด Starvation

[อ้างอิง: Lecture8_LocksMechanism.pdf หน้า 13-15]


======================================================================
8. Spin Waiting / Busy Waiting
======================================================================

Spin Waiting คือการที่ Thread รอ Lock โดยการวนเช็กซ้ำ ๆ

เช่น:

    while (lock ยังไม่ว่าง) {
        เช็กต่อไป
    }

Thread ยัง Running อยู่
ดังนั้นยังใช้ CPU

ข้อเสียหลัก:

    ใช้ CPU แต่ไม่ได้ทำ Useful Work

ถ้ามี Thread จำนวนมากแย่ง Lock เดียวกัน
หลาย Thread อาจใช้ Time Slice ไปกับการ Spin

ดังนั้นเวลาทำ PS08
ถ้า Algorithm มี Busy Waiting หรือ Spin Waiting
ต้องพูดเรื่องนี้ใน Performance Analysis ด้วย

[อ้างอิง: Lecture8_LocksMechanism.pdf หน้า 10, 14, 15, 24]


======================================================================
9. Compare-and-Swap (CAS)
======================================================================

CAS เป็น Hardware Atomic Primitive อีกชนิด

แนวคิด:

    ตรวจว่าค่าปัจจุบัน == Expected หรือไม่

ถ้าใช่:
    เปลี่ยนเป็น New Value

ถ้าไม่ใช่:
    ไม่เปลี่ยน

ทุกขั้นตอนเกิดแบบ Atomic

ตัวอย่างแนวคิด:

    Current value = 0
    Expected = 0
    New = 1

ถ้าค่าใน Memory ยังเป็น 0
CAS สามารถเปลี่ยนเป็น 1

ถ้ามี Thread อื่นเปลี่ยนค่าไปแล้ว
CAS จะไม่ทำการเปลี่ยนตามเงื่อนไข

CAS ใช้สร้าง Lock ได้คล้าย Test-and-Set
แต่แนวคิด Compare ก่อน Update ทำให้ใช้ประโยชน์ได้กว้างกว่าการสร้าง Lock อย่างเดียว

[อ้างอิง: Lecture8_LocksMechanism.pdf หน้า 16-18]


======================================================================
10. Fetch-and-Add และ Ticket Lock
======================================================================

Fetch-and-Add เป็น Atomic Operation ที่:

1. อ่านค่าเดิม
2. เพิ่มค่า
3. คืนค่าเดิมให้ Thread

อาจารย์ใช้แนวคิดนี้สร้าง:

    Ticket Lock

คิดเหมือนระบบกดบัตรคิว

ตัวอย่าง:

    Thread A ได้ Ticket 0
    Thread B ได้ Ticket 1
    Thread C ได้ Ticket 2

มีตัวแปร Global:

    turn

แต่ละ Thread รอจน:

    myturn == turn

เมื่อเลขตรงกัน
Thread นั้นเข้า Critical Section

ตอน Unlock:

    turn เพิ่มขึ้น

แล้ว Thread คนถัดไปจึงได้เข้า

ข้อสำคัญ:

- ช่วยควบคุมลำดับการเข้าได้ดีขึ้น
- Fairness ชัดกว่า Test-and-Set แบบธรรมดา
- แต่ Waiting Thread ยังสามารถ Spin อยู่ได้

[อ้างอิง: Lecture8_LocksMechanism.pdf หน้า 19-23]


======================================================================
11. ปัญหา "So Much Spinning"
======================================================================

แม้ Hardware-based Lock จะทำ Correctness ได้ดีขึ้น
แต่ถ้ารอแบบ Spin อย่างเดียว
Performance ยังมีปัญหา

ถ้ามี N Threads แย่ง Lock เดียวกัน

Thread ที่ได้ Lock:
    ทำ Critical Section

อีก N-1 Threads:
    อาจวนรอและใช้ CPU ไปเรื่อย ๆ

ถ้า Thread ที่ถือ Lock ถูก Context Switch ออก
Thread อื่นที่ Spin อยู่ก็ไม่สามารถทำให้ Lock ว่างได้เอง

จึงเกิดคำถามว่า:

    มีวิธีไม่ให้ Thread เสีย CPU ไปกับการรอหรือไม่?

[อ้างอิง: Lecture8_LocksMechanism.pdf หน้า 24]

12. Yield
======================================================================

แนวคิดต่อมาคือ:

    ถ้ายังไม่ได้ Lock
    แทนที่จะ Spin ต่อ
    ให้ Thread Yield CPU

yield() ทำให้ Thread:

    Running -> Ready

แล้วเปิดโอกาสให้ Scheduler เลือก Thread อื่นมาทำงาน

ข้อดี:

- ลดการ Spin ตรง ๆ

ข้อจำกัด:

- ถ้ามี Thread จำนวนมาก อาจเกิด Run-and-Yield ซ้ำ ๆ
- ยังมี Scheduling overhead
- ยังเสีย Cycle ได้
- Lecture ระบุว่ายังมีกรณีที่ Starvation เกิดได้

[อ้างอิง: Lecture8_LocksMechanism.pdf หน้า 25-26]


======================================================================
13. Sleep Instead of Spin + Queue
======================================================================

แนวคิดถัดมา:

    ถ้า Lock ไม่ว่าง
    ไม่ต้อง Spin
    แต่ให้ Thread Sleep

และใช้ Queue เก็บ Thread ที่กำลังรอ

Lock:

    ถ้า Lock ว่าง
        -> ได้ Lock
        -> เข้า Critical Section

    ถ้า Lock ไม่ว่าง
        -> เข้า Waiting Queue
        -> Sleep

Unlock:

    ถ้าไม่มี Thread รอ
        -> ปล่อย Lock

    ถ้ามี Thread รอ
        -> ส่ง Lock / ปลุก Thread ถัดไป

ข้อดี:

- ลด CPU Waste จาก Busy Waiting
- Queue ช่วยควบคุมว่าใครได้ Lock ต่อ
- สามารถช่วยเรื่อง Fairness / Starvation ได้

แต่การ Sleep/Wake ต้องใช้ OS Support

[อ้างอิง: Lecture8_LocksMechanism.pdf หน้า 27-29]


======================================================================
14. park(), unpark() และ setpark()
======================================================================

Lecture ใช้ Solaris เป็นตัวอย่างของ OS Support

มี Primitive:

    park()
    = ทำให้ Calling Thread Sleep

    unpark(threadID)
    = ปลุก Thread ที่ระบุ

แต่เกิดปัญหาหนึ่งได้ คือ:

    Waiting Race

ตัวอย่างแนวคิด:

1. Thread A กำลังจะ park()
2. ก่อนที่จะ park จริง เกิด Context Switch
3. Thread B ปลด Lock และ unpark(A)
4. Wake-up เกิดขึ้นไปแล้ว
5. Thread A กลับมาแล้ว park()
6. Thread A อาจ Sleep ต่อโดยไม่มีใครมาปลุกอีก

Solaris ใช้:

    setpark()

เพื่อบอกล่วงหน้าว่า Thread กำลังจะ park
และช่วยจัดการ Race ระหว่าง park/unpark

[อ้างอิง: Lecture8_LocksMechanism.pdf หน้า 27, 30-32]


======================================================================
15. Futex และ Two-phase Lock ใน Linux
======================================================================

Lecture กล่าวถึง Linux:

    futex

เป็นกลไกที่ให้ OS ช่วยจัดการ Waiting/Wakeup
โดยแนวคิดสามารถใช้ประกอบการสร้าง Lock ที่ไม่ต้อง Spin อย่างเดียว

Lecture ยังกล่าวถึง:

    Two-phase Lock

Phase 1:
    Spin ช่วงสั้น ๆ ก่อน

เหตุผล:
    บางครั้ง Lock อาจกำลังจะถูกปล่อยเร็ว
    การ Spin สั้น ๆ อาจถูกกว่าการ Sleep/Wake

Phase 2:
    ถ้ายังไม่ได้ Lock
    -> Sleep
    -> รอถูก Wake เมื่อ Lock ว่าง

ภาพรวมสำคัญ:

    Lock ที่ดีในระบบจริง
    มักไม่ได้อาศัย Software Algorithm อย่างเดียว

แต่เป็นการใช้ร่วมกันของ:

    Software
    + Hardware Atomic Support
    + Operating System Support

[อ้างอิง: Lecture8_LocksMechanism.pdf หน้า 33-34]

หมายเหตุจาก Research Notes ของเรา:

ถูกออกแบบให้ตอบ Mutual Exclusion, Progress และ Bounded Waiting

ไม่ควรเขียนว่า Peterson "มี Starvation โดยธรรมชาติ" โดยไม่มีเงื่อนไขรองรับ

อีกประเด็น:
ถ้าทำ Implementation ใน Modern C จริง
ห้ามถือว่า int/volatile ธรรมดาเป็น Synchronization Primitive ที่ถูกต้องโดยอัตโนมัติ

17. Load-Linked / Store-Conditional (LL/SC) อยู่ตรงไหน
======================================================================

Lecture กล่าวชื่อ:

    Load-Linked / Store-Conditional

เป็นหนึ่งใน Hardware Support for Locking

PS08 กำหนดให้เรา Research ตัวนี้โดยตรง

แนวคิดจาก Research Notes ของเรา:

LL/SC หรือในบาง ISA ใช้ชื่อ:

    LR/SC
    Load-Reserved / Store-Conditional

แนวทางทั่วไป:

1. LL / LR
   อ่านค่าจาก Memory
   และสร้าง Reservation

2. Software คำนวณค่าใหม่

3. SC
   พยายาม Store ค่าใหม่

4. ถ้า Reservation ยัง Valid
   SC สามารถสำเร็จ

5. ถ้า Reservation ถูก Invalidated
   SC ล้มเหลว
   และ Store ไม่เกิดขึ้น

6. Software มัก Retry

Pseudo-idea:

    do {
        old = LL(address);
        new = old + 1;
    } while (SC(address, new) == FAIL);

สิ่งสำคัญ:

    LL/SC ไม่ใช่ Mutex โดยตัวมันเอง

มันเป็น Hardware Primitive
ที่สามารถนำไปสร้าง Atomic Read-Modify-Write / Synchronization Mechanism ได้

ตัวอย่างสิ่งที่สามารถสร้างจาก LL/SC:

- Spin Lock
- Atomic Counter
- Lock-free Data Structure
- Synchronization Primitive อื่น ๆ

สิ่งที่ต้องวิเคราะห์ใน PS08:

- Reservation
- Success / Failure ของ SC
- Retry
- Contention
- Reservation Invalidation
- Correctness ของ Lock ที่สร้างบน LL/SC
- Fairness
- Performance
- Progress / Livelock concern ตาม Algorithm/ISA
- Memory Ordering

หมายเหตุ:
อย่าเขียนว่า "LL/SC รับประกัน Deadlock Freedom" แบบกว้าง ๆ
เพราะ Deadlock/Progress ต้องดู Algorithm ที่สร้างบน Primitive นี้ด้วย

       flag[2]

27. สิ่งที่ต้องระวังเรื่อง LL/SC
======================================================================

1. LL/SC เป็น Hardware Primitive
   ไม่ใช่ Mutex โดยตัวมันเอง

2. SC สามารถ Fail ได้

3. เมื่อ SC Fail
   Software มัก Retry

4. Contention สูง
   อาจทำให้ Retry บ่อยขึ้น

   แม้ค่าจะกลับมาเป็นค่าเดิม

   แต่รายละเอียดต้องอิง ISA/Architecture ที่นำมาอธิบายจริง
